# 主轮询循环（MVP runner）

> 由 VM 上的 cron 周期性拉起 TClaw 执行本循环（建议 2–5 分钟一次）。核心是**幂等状态机**：不重复处理、可重试、失败转人工。

## 状态机（AI待处理池.处理状态）
```
待识别 → 处理中 → (待补充 ⇄ 待识别) → 待确认 → 已入库 →（可选）已发布
                              ↘ 失败          ↘ 已退回
```

## 每轮步骤
1. **取活**：`record-search` 待处理池，过滤 `处理状态 ∈ {待识别, 待补充}` 且 `处理锁 = 否`，按上传时间升序，取前 N（如 5）。
2. **抢锁**（逐条，幂等关键）：`record-update` 置 `处理锁=是`、`处理状态=处理中`。若并发已被锁则跳过。
3. **处理**（统一 skill [物料版本管理](../skills/物料版本管理/SKILL.md)，各阶段照做）：
   - 新文件/信息不全 → 阶段一~二 入料·识别命名。
   - 识别完整、可定义 → 生成标准命名/版本号/风险标签，写 `AI识别结果`（阶段二）。
   - 信息缺失/冲突 → 阶段三 信息追问：写 `缺失信息`、设 `AI追问对象`、`处理状态=待补充`、释放锁。（自动化通知追问对象）
   - 可形成定义 → 阶段四 确认卡：填好待入库字段、`处理状态=待确认`、释放锁。（自动化通知上传者确认）
   - 用户回"通过" → 阶段五 入库写表（建主表+建版本记录+连两个关联，同步项交自动化）。
4. **人确认后**（下一轮轮询发现 `确认结果=通过`）：先读取池字段 `确认后自动发布(fld2avzfPJ)`。
   - `确认后自动发布=false/空`：按原入库流程写主表 + 版本表，`处理状态=已入库`，回执「已入库，可稍后发布」。
   - `确认后自动发布=true`：先完成原入库流程；等 7.5 建好主表并建好版本记录后，立即执行发布前门控：`python3 scripts/drive-upload/drive_uploader.py <主表record_id>` → 回读主表 `云盘链接M/L/S` 与 `是否大文件` → 写发布记录 → 主表 `发布状态=已发布`。
   - `确认结果=退回` → `处理状态=已退回`（自动化通知上传者）。
5. **失败处理**：异常 → `处理状态=失败`、`重试次数+1`、写 `处理日志`、释放锁。`重试次数≥3` 转人工（保持失败态，不再自动重试）。
6. **巡检（P1，独立 cron）**：扫描旧版外流、过期物料、长时间无人确认的待确认记录，发提醒。

## 幂等与并发原则
- 一切“认领”先抢锁；处理结束必释放锁（无论成功失败）。
- 写主表/版本表前先查重（内部物料ID/标准命名），避免重复入库。
- 自动发布前必须确认主表记录与版本记录都已存在；云盘链接未补齐时不发布，保留 `确认后自动发布=true` 等下一轮重试。
- 关键写操作前 `field-list` 校验字段 ID 与选项，避免脏写。
- 不在聊天里下结论：状态、识别结果、日志一律落 `待处理池` 记录字段。
