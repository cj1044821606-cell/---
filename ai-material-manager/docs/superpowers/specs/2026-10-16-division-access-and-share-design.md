# 储能事业部访问权限、市场部上传白名单与分享链接 · 设计

**全文摘要：** 把系统从“只认人员定义表”改为“按飞书部门开放”。储能事业部（含所有下级部门）的人都能打开系统，查看并下载全部已发布物料；上传权限给储能事业部下属的市场部，同时保留人员表里已有的上传角色；MCP 教程只对能上传的人自动弹出。另外，把空壳的“分享给客户”按钮改成“复制分享链接”，供事业部内部同事互相转发物料。部门 ID 存在系统配置表，前提是飞书应用补开部门读取权限。**预估阅读时间：** 7 分钟。

## 1. 背景与目标

- 现状：身份完全由人员定义表推导。表里只有 6 条记录，事业部里大多数同事打开系统都是“访客”，只能看到“全球 + 允许外发”的物料；分享按钮点了只弹提示，不生成任何链接；不能上传的角色（如销售）也会自动弹出 MCP 上传教程。
- 目标：
  1. 储能事业部全员都能打开系统，并下载已发布物料。
  2. 上传白名单 = 储能事业部下属市场部 ∪ 人员表现有上传角色。
  3. 不能上传的人不自动弹出 MCP 教程。
  4. 物料详情页可以一键复制分享链接，发给事业部内的同事。
- 不在本期范围：对外部客户的免登录公开链接（需要有效期、撤销、下载审计，另立项）；按部门自动推断区域；飞书后台“应用可用范围”的调整。

## 2. 已确认的决策（来自 2026-10-16 讨论）

| 问题 | 决定 |
|---|---|
| 分享给谁 | 事业部内同事，链接指向系统内物料详情页 |
| 事业部内、未录入人员表的同事能看什么 | 全部已发布物料：M、S 可下载，L 源文件不给 |
| 上传白名单 | 市场部（含下级部门）∪ 人员表中的策划 / 设计师 / 区域营销 |
| 怎么拦事业部以外的人 | 网站后端按部门判断，不依赖飞书“应用可用范围” |

## 3. 权限模型

### 3.1 身份新增字段（`shared/identity.ts`）

| 字段 | 含义 |
|---|---|
| `inDivision` | 本人任一所属部门，或其任一上级部门，是配置中的储能事业部 |
| `inMarketing` | 同理，命中配置中的市场部 |
| `canAccess` | `inDivision` 或 在人员表中有记录 |
| `isUploadRole`（改口径） | `inMarketing` 或 人员表角色含 策划 / 设计师 / 区域营销 |

`isVisitor` 保持“人员表里没有角色”的原义，继续用于“不提供编辑类功能”等现有判断。新增的 `isDivisionMember`（= `inDivision` 且 `isVisitor`）专门用于放宽可见范围。

### 3.2 规则表

| 情况 | 能否打开 | 可见物料 | 下载 | 上传 | 自动弹 MCP 教程 |
|---|---|---|---|---|---|
| 不在事业部、不在人员表 | ✗ 无权限页 / 接口 403 | — | — | ✗ | ✗ |
| 事业部内、不在人员表 | ✓ | 全部已发布 | M、S | 市场部 ✓，其他 ✗ | 仅能上传的人 |
| 在人员表，总部 | ✓ | 全部已发布（不变） | 按角色（不变） | 市场部 或 上传角色 | 仅能上传的人 |
| 在人员表，区域 | ✓ | 默认本区域，可切换“查看全球”（不变） | 按角色（不变） | 市场部 或 上传角色 | 仅能上传的人 |

- 物料可见性：`isMaterialVisible` 中，`isDivisionMember` 与总部同等对待（只看已发布，不受区域限制）。
- 源文件 L 的可见角色不变（设计师 / 策划 / 维护者）。
- MCP 接入：凡 `canAccess` 都可以在“更多”里手动开启，用于搜索和下载。`whoami.canUpload` 与 `prepare_upload(s)` / `publish_material` 都改用新的 `isUploadRole`。
- 教程自动弹出条件：由 `!isVisitor` 改为 `isUploadRole`。手动重看入口对所有 `canAccess` 用户保留。

### 3.3 部门判断

- 部门配置存在系统配置表（`tblyZv7k70fD64un`）的两条新记录里，改部门不需要重新部署：
  - `access_department_ids`：文本值为储能事业部的 `open_department_id`，可填多个，逗号分隔。
  - `upload_department_ids`：文本值为市场部的 `open_department_id`。
- 新增 `DepartmentService`：
  1. 用 `GET /open-apis/contact/v3/users/:open_id`（`department_id_type=open_department_id`）取 `department_ids`；
  2. 对每个部门调用 `GET /open-apis/contact/v3/departments/parent` 取完整上级链；
  3. 本人部门与上级链合并成集合，再和两组配置 ID 求交集。
- 缓存：用户部门链缓存 30 分钟；部门 → 上级链缓存 6 小时。身份本身的缓存保持 10 分钟。
- 以 tenant 身份调用。应用的通讯录权限范围必须覆盖储能事业部。

### 3.4 失败与降级

| 情况 | 行为 |
|---|---|
| 部门配置缺失或为空 | 退回现有规则：只认人员表。运维页显示“部门权限未配置” |
| 部门接口报权限不足（如 99991672 / 99991679 / 40004） | 在人员表的照常放行；其他人返回 503 和“暂时无法验证部门，请稍后重试”。记日志，运维页告警 |
| 部门接口偶发失败 | 重试 1 次；仍失败按上一行处理，并且不写缓存，避免把失败结果缓存住 |

设计原则：部门服务出故障时，不把原本能用的人挡在门外。

## 4. 访问拦截

- 在全局登录守卫之后加一道 `DivisionAccessGuard`：`canAccess=false` 时，接口返回 403 和 `{ code: "NOT_IN_DIVISION" }`。
- 前端在 `/api/auth/me` 或任一接口收到 `NOT_IN_DIVISION` 时，显示“无访问权限”页：说明本系统仅对储能事业部开放，如有需要请联系维护者，并给出退出登录按钮。
- 不拦截的路径：`/healthz`、`/api/auth/*`、下载签名代理（签名时已绑定用户，生成签名的接口本身已经过拦截）。
- MCP：令牌主人 `canAccess=false` 时，所有工具返回同样的错误文字；签发令牌的接口也要求 `canAccess`。

## 5. 分享链接

- 详情页把“分享给客户”按钮改为“复制分享链接”（图标 `Link2`）。点击后把 `${window.location.origin}/material/<baseRecordId>` 写入剪贴板（前后端同域，线上即 `https://materials.caojunaimcp.com`），并提示“已复制，储能事业部同事打开即可查看”。
- 剪贴板不可用时（如部分飞书内置浏览器），改为弹出带只读输入框的对话框，让用户长按复制。
- 不再受“允许外发”闸门限制：链接只对事业部内部有效，外发规则仍体现在物料的外发标识上。复制提示里加一句：对外请先确认“允许外发”。
- 物料库卡片：在卡片右上角新增一个复制链接的小图标按钮。桌面端悬停时显示，手机端常显；点击时不跳转到详情页。
- 未登录打开链接：沿用登录接口已有的 `next` 参数，登录后回到该物料。
- 打开的人看不到这条物料时（区域限制或已下架），显示现有的“物料不存在”空状态，并提供“去物料库”入口。
- 原 `ShareDialog.tsx` 删除，相关 i18n 文案一并清理。

## 6. 需要你在飞书后台做的事（一次性，是前置条件）

1. 进入开发者后台应用 `cli_a95252e698f9dbca` → 权限管理，开通以下权限（名称以后台搜索结果为准）：
   - 获取用户所属部门：`contact:user.department:readonly`
   - 获取部门基础信息：`contact:department.base:readonly`
2. 在“通讯录权限范围”里确认包含储能事业部，否则接口拿不到事业部成员的部门信息。
3. 创建版本并发布。
4. 发布后告诉我。我会以你本人为样本回读部门链，按名称确认“储能事业部”“市场部”的部门 ID，写入系统配置表并回读，然后再部署代码。

## 7. 测试

- 单元测试：
  - 部门链：多层嵌套、一人多部门、市场部是事业部的下级、配置里有多个 ID。
  - 身份口径：四种人群 × 是否在市场部。
  - 失败降级：配置缺失、权限不足、接口偶发失败，以及失败结果不写缓存。
  - 守卫：403 返回码和放行白名单路径。
  - MCP：`canUpload` 的新口径，非事业部令牌被拒。
- 前端测试：教程自动弹出条件；分享按钮的剪贴板成功和失败两条路径；无权限页。
- 本地预览（连真实 Base，只读）：用你本人账号验证部门链和权限。非事业部账号的拦截用测试替身验证，不拿真实同事账号试。
- 上线后：用你本人账号在飞书内打开分享链接，确认登录后自动回到物料页；运维页无部门告警。

## 8. 上线顺序

1. 飞书后台补权限并发布（你做）→ 我回读确认部门 ID → 写入两条系统配置并回读。
2. 代码 PR → CI → 合并 → 部署到 Google VM，保留回退镜像。
3. 部署后核验：本人账号 `/api/auth/me` 返回 `inDivision` / `inMarketing` 正确，物料库条数符合预期，分享链接可以打开。

上线时如果部门配置还没写好，系统会按 3.4 退回“只认人员表”，所以代码可以先于配置上线，不会把现有用户挡在门外。
